# 业务风险分析方法

## 先建立可解释的业务基线

提取本次实际材料支持的对象、规则、变更和路径：

- 对象身份及归属：谁拥有，谁能访问，怎样区分同名记录，权威源在哪里。
- 关系与传播：主从记录、快照/副本、计算值、写回、读者及下游。上游变化是否传播应引用规则或标未知。
- 生命周期：创建、维护、提交、审批、取消、失效、结束及恢复中，适用的合法动作与权限。
- 业务结果：金额、数量、币种/精度、日期时区、状态及关联约束。举例数字标示假设，不冒充规则或实际记录。
- 本次变更影响：旧/新行为及不变基线，历史记录、迁移与兼容是否确实受影响。

不要把功能名或控件清单直接当风险；风险应说明具体错误及可理解的后果。

## 按实际失败机制展开

| 适用场景 | 需要分析的失守位置 | 后果与证据边界 |
|---|---|---|
| 金额/结算 | 取错对象、漏项/重复、币种方向、舍入层次、人工值覆盖 | 描述具体错算或错付路径，不凭“涉及金额”认定全部不可接受 |
| 身份/权限 | 同名不同ID、跨归属、角色或状态门禁遗漏 | 区分界面禁用与服务端控制，引用各自实际证据 |
| 状态/关联 | 非法迁移、主从不同步、关联失效、源/副本错误传播 | 列触发条件和受影响对象，不自行发明级联规则 |
| 多阶段写入 | 前一步成功、下一步失败后已经存在的记录/状态/外部动作 | 是否允许部分成功、如何恢复取已确认规则；没有规则先标待确认 |
| 结果未知/重试 | 提交已发生但响应丢失，重试关联身份和重复副作用 | 超时只说明结果未知，不能当作写入失败或已经重复 |
| 并发/旧页面 | 竞争窗口、晚到写入、重复消费、覆盖更新 | 说明需要什么并发或时序条件，普通顺序操作不能证明这些条件 |
| 历史/迁移 | 映射、重复/遗漏、新旧口径分界及历史快照 | 旧记录未读到不是迁移有缺陷，缺基线须说明影响 |
| 外部/异步 | 接收、处理中、终态、补偿及上下游不一致 | 请求接收不等于业务完成；未取得下游证据不扩大结论 |

这些是适用时的分析角度，不是每项需求必须展开全部类型。UI细节仅在形成具体业务错误或关键可用性后果时按实际影响排序。

多阶段场景可用小表：阶段 → 已产生的业务事实 → 本步失败/未知后的可能状态 → 现有防护/恢复 → 证据及验证缺口。不把它写成已执行日志。

## 事实、判断和控制分别记录

规则依据：已确认 / 待确认 / 有冲突 / 资料未取得。实现与观测另外注明类型和适用版本。一个风险可有多个来源，来源冲突保留双方，不用代码当前如此或较新日期自行裁定。

风险判断：有依据的潜在风险 / 假设待核实 / 本范围已排除或撤销。实际出现的反例须引用证据，并注明是否已经确认为产品缺陷；仅写风险不能宣称发生过。

控制情况：仅有方案 / 实现已定位 / 当前范围有验证证据 / 未知。控制验证须指向对象、条件、断言、环境/版本及结果范围。脚本存在、页面显示禁止、唯一索引描述、历史通过各自只支持已取得的事实。

风险后果与控制后的剩余风险分开。未验证控制写“剩余风险尚不能判断”，不要凭措施名称判已消除。反证或有效替代出现后重评，不固守第一次定级。

## 排序与接受

项目已有风险标准、验收决定或业务确认时，引用其适用依据。没有时可按具体损失严重性、暴露条件、影响对象范围和可发现/可恢复程度给建议先后，并说明未知项，不硬造发生概率或乘积评分。

直接后果与进一步后果分开；进一步后果要写成立条件和依据。不要从一个字段错误无条件推到资金损失、合规处罚或无限连锁事故。

高影响、低置信度的项保留优先核实，不用未知概率降为低风险。当前用户排除的范围记录理由与未评估影响，不偷偷扩大分析或称其风险为零。

“接受风险”“延期验证”“无需处理”必须有适用决定和来源；分析者只能建议。风险接受决定及有效期限/范围未知时留待业务决策，不编造Owner、日期或承诺。

## 交接

每项交出稳定风险编号、场景、依据、主要约束、优先级理由、建议验证目标、所需观察渠道及未决问题。可引用已有用例/测试证据，但不新写完整测试步骤、不执行验证。

独立分析可直接消费需求；无需先运行别的 skill。需求已给出明确规则则复用，未决仅阻断依赖它的结论。后续用例设计保留风险编号，避免再维护一套无映射风险。
