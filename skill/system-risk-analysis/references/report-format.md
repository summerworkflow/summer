# 《业务风险分析》交付格式

采用适合本次材料的篇幅，先给最影响决策的风险和缺口，再给来源与明细。主报告不只交一张术语大表；复杂风险给一个能理解的业务例子，并标明是否为假设。

## 范围与基线

- 分析批次、skill 版本、适用业务/需求版本、分析日期。
- 本期目的与旧/新行为；已分析、部分分析、未读和明确排除范围。
- 来源索引：ID、名称/位置、材料类型、适用版本、读取状态及实际指纹。缺信息写未知，不伪造。
- 相关对象关系与流程简述，可用小表；无需为简单任务画复杂模型。

## 风险总览

按优先处理顺序列 RISK-001 等稳定编号、标题、建议/已确认优先级、判断状态、直接后果及下一步。风险总览和详情引用同一编号。条数是分析条目数，不是缺陷数、覆盖率或风险得分。

## 单项风险

~~~markdown
### RISK-001｜提交成功后响应丢失，重试可能重复付款

- 场景与触发：两个请求是否使用同一业务身份，第一次可能已提交而客户端未收到终态。
- 可能失守：重试生成新交易且未识别原提交；这是待核实机制，不能写成已发生缺陷。
- 直接后果：同一义务可能重复支付；进一步后果按真实依据说明。
- 关联：变更/规则编号、对象和状态；来源定位及版本。
- 判断与依据：已确认的规则、已定位实现、实际观测、假设和冲突分别列出。
- 现有防护及证据：保留实际已知控制及验证范围；未查明就写未知。
- 处理顺序：引用项目口径；没有时写建议优先级及理由、未知因素。
- 建议验证重点：核对原交易身份、提交后超时状态、重试及实际付款笔数的关联。
- 所需证据：足以证明付款终态及次数的记录；仅页面提示不足以判断。
- 缺口与下一步：关联Q编号、待补材料或决策、实际责任角色；具体人/期限未知则待定。
- 剩余风险/接受：未取得控制验证时尚不能判断；有接受决定时引用其范围和来源。
~~~

上述为虚构格式示例，不是实际付款规则、缺陷、风险核定或执行证据。字段可合并表达，但不能省掉判断依据和未知项。普通非资金风险按实际机制写，不套付款故事。

## 待确认与验证交接

只列影响风险判断或验证方向的精确缺口，引用已有需求Q编号；缺口本身不冒充风险，也不复制整份需求问题清单。每项说明影响哪些风险、需要补什么及独立工作是否能继续。

交给设计的清单保留风险编号、范围、已确认依据、建议验证目标和渠道边界；关联现有用例仅记录实际映射。风险分析产物不是完整用例，更不是发布准入决定。

## 修订

保留前批次引用及风险ID映射，写新增、调整、拆并、撤销及依据。低风险不等于可删除，已采取措施不等于验证完成。变更材料或风险逻辑后新建批次，反馈记录跟随其实际版本。
