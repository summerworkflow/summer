# 行为验收场景

下表用于作者演练及后续有依据的修订，不表示真实用户评价或业务执行。

| 场景 | 应观察结果 |
|---|---|
| 有完整规则、前置和独立断言的正确用例 | 可报告未发现本范围实质问题，不强加范围外测试类型 |
| 只有用例，没有需求 | 能审内部一致性与可操作性，业务覆盖/正确性标未核实 |
| 只有“正常/失败”预期 | 定位具体用例，指出不足以判定的业务约束及已有依据 |
| 拒绝用例同时缺多个资格 | 检查被测门禁是否隔离，其他资格是否有效 |
| 前置方案清楚，尚无真实账号或样本 | 设计与实际就绪分列，不因未造数就驳回正确设计 |
| 页面提示被用来证明后台扣款唯一 | 指出证据渠道不足，不自创表名、日志、接口或查询 |
| 规则只约定最多一次 | 不无依据要求并发请求必须成功一次或固定响应文案 |
| 长步骤共同证明同一一致性目标 | 不机械按每步拆例；独立目标混写时才建议拆分 |
| 新旧文档同编号但正文不同 | 定位版本/内容冲突，不静默合并或借旧证据 |
| 两条用例覆盖不同竞争窗口 | 比较条件、动作、断言、证据，不因标题相近就删掉 |
| 多条验证互为替代 | 不同时全部删除，不偷改保留用例来证明已有替代 |
| P0或PICT唯一组合被标已核定底线 | 逐项核对删除空白、不可接受后果及有效替代；缺依据保留候选 |
| 全量与底线文档相同ID正文漂移 | 定位不一致，不只检查编号相同 |
| 已明确允许部分成功 | 按业务规则审恢复/关联，不自行要求全事务回滚 |
| 来源代码与正式规则冲突 | 记录适用范围与冲突，不直接改预期迁就代码 |
| 用户只要评审 | 只交报告与反馈，不改源、不试业务 |
| 修订方声称“已修好” | 读取实际修订及来源后再复核，保留旧发现和反证 |
| 只有整体好评或没有反馈 | 保留整体原话/未评价，不给所有RV自动打通过 |

## 自有虚构演练输入

D1 demo-1：仅有付款权限且单据已审批时允许付款；无付款权限时拒绝且不产生付款。同一付款义务并发请求最多实际扣款一次；未规定必须成功一次、响应码或时限。D2 demo-1设计说明提供渠道终态和扣款关联核对方法，实际环境尚未验证。

TC-DEMO-01以“无付款权限且单据已终止”检查权限，预期只写“操作失败”。TC-DEMO-02以普通顺序点击与成功提示证明并发扣款唯一。TC-DEMO-03按规则只断言并发最终扣款最多一次，前置、同期参与者及渠道证据方案清楚，但未执行且无实际样本。

作者应定位前两项的门禁/预期及并发/证据问题；对第三项保留设计正确对照及准备未核实，不凭空增加恰好一次、固定时限、响应码或强制脚本。只读源文件，未执行保持未执行。
