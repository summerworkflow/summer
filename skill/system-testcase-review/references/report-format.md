# 用例评审报告与可复核发现

报告先说明对本阶段的结论及最重要问题，再给范围和明细。用户可直接据此修改，不必二次翻译术语。

## 范围与结论

记录评审批次、skill版本、材料/用例版本及哈希、已读/未读范围、规则和风险来源。评审依据缺失时精确说明哪些判断受限；不能仅凭用例自洽就认定全需求完整。

结论按实际范围选择：

| 结论 | 使用条件 |
|---|---|
| 可交付 | 本次约定检查未发现阻碍交接的问题，范围和限制清楚 |
| 有条件可交付 | 明确子集可继续，具体未决项及受限范围列明 |
| 需修订 | 已定位到影响本阶段交接的实质错误、缺口或不可判定项 |
| 无法完整判断 | 关键依据或评审范围尚不足，说明仍完成哪些检查 |

结论为评审建议，不冒充已有人工/业务/发布批准。真实批准记录仅在已取得时按来源、对象和版本登记，不凭空要求每次重新审批。

## 每项发现

给稳定 RV-001 等编号。至少写：

- 位置：具体用例/断言、规则/风险编号、文档章节/行或表名行范围，及适用版本。
- 问题与类型：已经核实的设计问题、待补材料/待裁定，或可选优化；事实、推断、建议分开。
- 后果和处理顺序：会漏掉什么、错判什么或阻塞哪一分支，严重性/优先级沿项目口径；无口径给有理由的建议。
- 证据：用例实际内容及适用规则定位，不能只写“根据最佳实践”。
- 最小修订方向：明确改哪一前置/断言或补哪种场景，已知的填实，未知的不编造。
- 复核条件：改到什么程度可以确认本项关闭；提供文档修订不等于已复核。

相同原因、同一修改可以关闭的发现合并，保留全部受影响ID。不同问题不因同属一个用例就混成大项。

## 虚构格式例子

假设需求R1规定“无付款权限时拒绝且不产生付款”。用例TC-01以“无权限＋付款单已终止”为前置，预期只写“操作失败”。

RV-001：TC-01没有隔离角色门禁，可能因已终止而失败，无法判定R1是否生效。依据是TC-01前置与R1，建议使用其他资格有效的对象、只缺付款权限，并核对拒绝及无付款副作用。具体拒绝码和真实数据若未提供则不编造。复核时检查前置资格与断言已对应R1；没有实际运行时执行状态仍未执行。

这只是作者示意，不是项目规则、已执行反例或产品Bug。

## 其余内容

按业务目标简述覆盖去向、重要缺失场景、保留正确项或无问题范围；不复写全部用例。列修改/补测建议的先后及依赖，顺序服务于设计修订，不在本任务自动试跑。

报告剩余风险、待补材料、实际未做检查和建议交接对象。全部只审了部分时明确，所需真实就绪核验与静态设计评审分列。

## 复核

重读实际修订文件和适用依据，核对指纹/版本及问题位置；按原RV编号记录仍存在、已修订待复核、复核关闭、撤销/误报或待裁定。源变化后建新评审批次并关联旧问题，保留反证与修订理由。

不因修订者写“已修复”、机械校验通过或其他用例通过就关闭业务评审问题。结论影响范围改变时重新说明，不清空旧报告。
