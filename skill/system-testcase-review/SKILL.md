# 测试：用例评审

版本：1.0.0。调用 $system-testcase-review。历史见 [CHANGELOG](CHANGELOG.md)。

## 职责

已有用例与适用依据 → 对照业务目标和可验证性审查 → 可定位、可修改、可复核的评审结论。

用于审阅人工、AI或存量用例，以及修订后的复核。默认只读源用例和依据，交付评审问题及建议；不自动修改用例、编写业务脚本、登录系统、准备真实数据或执行测试。用户同时要求修好时，按既有授权衔接设计修订，再复核本轮问题，不重复索要已授权确认。

写用例时的自查、格式转换校验和本次评审分别说明；同一作者完成的语义自查不能宣称独立外部验收。评审可交付建议不等于测试通过、风险接受或发布批准。

## 评审主线

1. **固定本次对象**：读取指定用例、全部/底线文档、适用需求及答复、风险分析和已有评审；记录版本、指纹、编号和实际范围。复用已有材料，不要求重走全部前序阶段。缺需求时先做内部一致性、步骤及证据方案审查，覆盖正确性标未核实。
2. **从业务依据重建检查基线**：按 [评审检查](references/review-checklist.md) 对照变更、确认规则、风险、对象关系、状态及角色，找应验证的目标。再反查每条用例的来源和独立断言；标题相似、表格有编号或代码已实现都不能单独证明覆盖。
3. **逐条判断是否测得到、判得对**：检查目标、合法前置及数据分配、操作入口、步骤与预期关联、独立算例、观察方式和影响处理。设计方案与本轮真实就绪分开；实际账号/样本未核实不自动否定正确设计。复杂交易链围绕一个目标时不机械拆成每步一例。
4. **检查重复、修订和底线**：比较条件、动作、断言及证据能力，保留实质不同的路径；对照旧版检查删除理由和纠错影响。若有底线文档，按三条件复核及两份正文一致性，候选与已核定分开，不把高风险或唯一参数组当已核定。
5. **输出能直接处理的发现**：按 [报告格式](references/report-format.md) 给稳定 RV 编号、对应规则/风险/用例/断言及位置、问题、后果、证据、最小修订方向和复核条件。按业务影响排序，材料不足、设计问题与优化建议分开，不凑问题数量。
6. **复核和交付**：确认每项有证据、范围和改法，检查是否误报已有正确内容，是否把未知/未读范围当成不存在。只做了抽样就说明样本及未审范围，不宣称全量。保留未关闭问题和依赖，明确部分继续。

按需采用已有真实校验器核对匹配协议的文件；先检查其入口和行为。校验未运行如实记未做，不为评审执行未知脚本。静态文件校验和语义评审分别报告，都不能替代业务实测。第三方检索与取舍见 [借鉴来源](references/borrowed-sources.md)，运行本技能无需联网或安装第三方技能。

## 结论与交接

以本次明确阶段为范围，给“可交付”“有条件可交付”“需修订”或“无法完整判断”，逐项说明依据、条件和未核实范围。没有评审发现可以正常交付；不为显示专业制造规则、扩大范围或强行驳回正确用例。

默认输出 用例评审报告.md 与 用例评审反馈.md，放项目本批次目录；仅需对话时按用户要求给结果及必要反馈定位。报告包含来源、审查范围、问题明细、覆盖去向、修改顺序及剩余风险；不是整套新用例。用户指定其他格式时保留相同含义。

修改意见交给设计；规则冲突引用已有Q或指出具体待裁定；真实环境、能力与样本缺口交给前置准备；证据方案不足说明所需渠道。不自动启动后续流程，也不凭高星仓库的示例通过率、时限或框架约定裁定本项目。

## 版本与实际效果

skill版本、用例/材料基线、评审批次和反馈revision分别维护。源用例或规则变化后创建新批次，保留原RV编号与去向；问题已改、已复核和产品已修复/测试通过分别表示。

按 [效果回收](references/outcomes.md) 保留真实采纳、误报、漏审、修订复核及可读性反馈。“查看这次用例评审效果”时只读指定报告与反馈，先列未关闭重要问题、争议和反证，再展示实际使用情况。未评价/无使用记录如实说明，不用发现数量、关闭率或作者自审冒充技能收益。

检查行为场景见 [验收场景](references/acceptance.md)。改进以具体证据和反例为依据，用户授权维护时小步修改并升版，不自动写知识库、联系他人、遥测或安排回访。
