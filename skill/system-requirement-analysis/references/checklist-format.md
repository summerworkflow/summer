# 待确认清单：写法与示例

用户应该能直接拿去沟通，不需要再次把分析术语翻译成问题。

## 每个问题的写法

以下是组织内容的参考，不强制逐项套同一句话。资料待补、旧规则待查和配置待定也可更短，不能伪装成业务缺口。

~~~markdown
1. **Q001｜船卸完货后又去加油，“预计空船”显示哪一站？**

   场景和例子：以下是假设例子。20日在甲港卸货离港，22日在乙港加油离港；用户没有手填预计空船。

   现在的问题：资料A要求取卸货港时间地点，得到“20日甲港”；资料B按最后港时间、合同卸港地点取值，可能得到“22日甲港”。

   可以直接问产品：“请明确这个例子最终显示哪一天、哪个港口，并把两份资料改成一致。”

   建议：时间和地点应对应同一次业务，避免把两站拼在一起。具体采用哪次业务需产品确认。

   影响：相关字段自动带出和测试预期；不影响人工保存动态等独立场景继续设计。

   类型：规则冲突。状态：待确认。
   依据：资料A的适用版本与章节；资料B的工作表和单元格。保留可点击位置或最小摘录。
~~~

保留足够细节让接收方给出确定答案，不机械要求每题同样长。负责人只写已知角色；不知道具体人员时写“产品负责人（具体人员待定）”，不编造姓名或期限。

## 把大题缩成具体问题

不宜：“请明确损益算法、字段协议和幂等规则。”

可用：“委托已经保存，但付款申请没打开。用户再次点击时，会继续使用这张委托，还是新建一张？请开发先说明现有流程怎样处理；如果没有继续操作的入口，再请产品确认入口和提示。”

这里讨论的是一次失败后如何继续，不顺手扩大成全部费用算法、全部付款权限或数据库事务设计。

## 三个容易写错的地方

### 在线表没读到

不宜：“确认表的必填、长度和编辑权限没有规定。”

可用：“原型指向在线最终字段表，本轮未能读取。先取得该版本，核对‘联系人不填能否保存’；表里已有答案就直接引用，缺的部分再列问题。”

状态是“待资料”，不能据此给产品记一个规则漏项。

### 本来已有规定

如果材料明确“未保存不能下载PDF”，就直接作为后续设计依据。不能再问用户“要不要先保存才能下载”。

旧分析把它标成待确认时，保留撤销记录和现有依据；不把撤销伪装成新发现，也不算成产品新回答了一题。

### 把自己的建议当规则

“建议保留已保存委托，让用户继续申请付款”是待确认建议。
只有实际取得适用确认依据，才能记录为已确认答案。不能写成“系统应该这样，所以当前实现是Bug”。

## 输出前的内容检查

每一项都应能回答：

- 在什么前置状态下，谁做了什么，哪个结果无法判断？
- 这个缺口来自哪份已读资料，还是有哪份资料没读到？
- 接收方可以回答一个明确结果，还是仍要自己拆题？
- 举例是原材料中的事实，还是明确标注的假设？
- 建议是否有理由并保持未确认？没有依据时是否选择先查资料？
- 解决这个问题，会解锁哪些分支？是否误把无关分支也阻塞？

不要给可读性编造分数或“用户一定能懂”的结论。自审通过只代表完成自审，实际效果以用户反馈为准。
