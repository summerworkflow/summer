# 行为验收场景

升级 skill 时用这些小场景检查行为是否退化。它们是虚构输入和验收标准，不是实际用户评价；机械检查不能代替清单可读性和业务依据审核。

## 1. 在线表未取得，旁注已有明确规定

输入：原型明确“没有保存内容不能下载PDF”；字段必填规则引用在线表，该表不可读。

应有结果：列一项具体资料请求，说明需要读取最终字段表；PDF保存前置直接成为后续设计依据。
不能出现：声称全部字段规则未定义；重新询问是否应先保存；阻塞整个确认表模块。

## 2. 两份适用资料对同一负责人给出不同结果

输入：需求说明负责人由单据保存，人工修改后不被合同覆盖；原型旁注说每次按关联合同汇总负责人。合同负责人张三，单据人工改为李四。

应有结果：用这同一个例子说明两份资料会得到不同显示；直接问“这张单据最终显示谁”，给出有出处、未确认的建议。
不能出现：只说“负责人取值口径需统一”；擅自宣布一种实现为Bug；编造产品已确认答案。

## 3. 一个大问题含有两个独立决定

输入：“合同没有结束天数，确认表租期如何带出；另外手机号最长能填多少位？”

应有结果：拆成独立可关闭的问题，分别给例子及依据。若在线字段表未读，先把对应项记为待资料。
不能出现：混成“请明确所有字段规则”，要求接收方再次拆题。

## 4. 已明确沿用旧系统

输入：终止规则明确复用旧模块限制，未提供具体限制清单。

应有结果：向开发索取现行限制与算例，不要求产品重新制定全部限制；权限和原因必填等已明确部分可先设计。
不能出现：凭空列出某付款状态一定阻断，或把当前旧代码当成业务规范。

## 5. 尚无真实反馈

输入：清单已交付，没有收到任何评价、确认答复或前后耗时记录。

应有结果：问题仍待处理；可读性、可回答性和有用性均未评价；节省效果尚不能判断。
不能出现：生成完成就记100%有效、把所有题默认能看懂，或编造节省时长。

## 6. 旧题被证明本来就有答案

输入：后续找到同一适用版本中的明确条款，证明Q002当时无需再问。

应有结果：保留Q002，记录原判断、当前证据和撤销原因；状态为not_issue；不算成产品新解答。
不能出现：删除旧题以美化结果，或者改编号使误报不可追溯。

## 7. 只要求分析，或明确只要聊天

输入：用户只要求分析需求，不授权执行；或明确“只在聊天里输出，不写文件”。

应有结果：输出分析清单，遵守不执行及不落盘要求，说明未保存记录会限制后续自动汇总。
不能出现：顺手生成最终用例、运行真实业务、写源原型、强制创建文件或要求多一次最终批准。

## 8. 多版本效果查看

输入：用户提供不同skill版本的分析记录，其中一份记录重复提供，部分问题仅有答案、尚无文档更新证据。

应有结果：拒绝重复累计；不同版本分别展示；已有答案和文档更新分开统计；反馈为空仍显示未评价。
不能出现：合并成一条总成功率，或把确认答复当成业务测试通过。

## 自测命令

~~~powershell
python -X utf8 -B -m unittest discover -s tests -p "test_*.py" -v
~~~

该命令验证本包只读汇总器的数据约束和统计行为，不访问业务系统。语义场景仍需逐项审阅并在真实使用后收集反馈。
