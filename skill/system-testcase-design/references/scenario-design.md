# 场景设计

用于存在生命周期、权限、字段联动或上下游影响的需求。按与本次目标有关的维度选择分析深度；不把下表机械展开成所有组合。

## 从业务对象到场景

先梳理对象及关联关系，识别业务规则约束的是单个对象、对象之间的关系，还是整个处理链路。页面和接口可作为入口索引，不代替业务路径。

| 维度 | 需要识别的差异 | 场景选择依据 |
|---|---|---|
| 生命周期 | 初始、处理中、终止、撤回、重试；合法及被禁止的转换 | 覆盖本次相关转换、转换资格和关键终态；已明确禁止的动作验证无副作用 |
| 角色与数据范围 | 操作权限、对象归属、跨组织访问、当前处理人 | 区分有权、无权和有操作权但无对象访问权；只展开真实存在的角色与范围 |
| 数据及关系 | 空值、边界、精度、唯一性、父子对象、汇总和引用关系 | 围绕规则分区，检查关联约束和跨对象一致性；边界值来自明确规格 |
| 入口及链路 | 页面、接口、导入、批量入口、上下游和历史数据 | 覆盖本次存在且可能产生不同结果的入口；客户端限制不能证明服务端约束 |
| 失败与恢复 | 超时、拒绝、部分成功、结果未知、补偿与重试 | 检查错误结果、残留副作用及恢复路径；不存在的故障注入能力列为前置缺口 |
| 时序与竞争 | 重复提交、并发修改、撤回与执行竞争、消息重复或乱序 | 仅在共享状态、异步处理或重复入口确实相关时展开，并说明要守住的业务约束 |

非功能场景按需求与风险选择，例如性能容量、兼容性、可访问性或隐私。目标指标未确定时提出问题；不能自行发明响应时限或容量承诺。

## 用约束组织覆盖

优先识别“无论怎样操作都应成立”的业务约束，例如对象关系一致、权限不越界、总额守恒、终态不可被非法改写。每项约束均须有本次依据；“常见最佳实践”只能形成候选问题。

对一项规则，按实际适用性选择：

- 一个能够证明主要路径成立的有效场景。
- 能改变规则判定的条件分区和有依据的边界。
- 能绕开限制或破坏关键约束的反例。
- 与本次变更有关的失败、恢复、相邻流程或回归场景。

对金融或高影响场景，把金额、币种、精度、时点和汇总范围作为规则的一部分；示例计算不能代替正式口径。

## 覆盖关系

可用以下紧凑表承载；一行表达一个具体规则或风险场景，避免用“全部权限”“所有异常”作为不可核查的覆盖项。

| 范围项／规则 | 场景与具体风险 | 用例 ID | 覆盖状态及缺口 |
|---|---|---|---|
| 来源定位及规则 ID | 条件、动作、潜在错误及后果 | 已设计用例或空 | 已覆盖／部分覆盖／待决阻断／排除及理由 |

“已覆盖”仅表示设计上覆盖声明的目标。页面用例仅观察到提示时，业务落库或外部处理仍应标为部分覆盖或另设验证用例。

排除说明边界，例如某接口不在本次版本范围、某状态在合法流程不可达。无法准备、规则不明确或工具不支持属于缺口，不作为低风险排除理由。

## 规模控制

- 先保证关键规则与高风险有覆盖，再增加有价值的组合；不做全维度笛卡尔积。
- 相同规则下的等价输入可参数化；权限含义、状态路径或预期不同的场景保留各自判定。
- 风险优先级与设计／准备状态分别记录。高优先级用例也可能等待规则确认；低优先级用例也可能已具备执行条件。
- 不用固定数量衡量充分性。存在统计口径时才给覆盖率，并公开分母、部分覆盖与待决项。
