# 用例契约

本文件维护用例字段、状态和上游问题的唯一约定。2.0.0默认交付两份可读文档及一份索引反馈记录。相同ID正文一致，底线判断按[底线筛选](bottomline-selection.md)，批次及记录按[记录与回收](record-and-review.md)。

## 原子用例字段

字段可以用表格列、逐条小节或结构化属性表达。重复的依据、准备或隔离方案可集中定义并引用，引用须能定位到具体内容。

| 字段 | 要表达的内容 |
|---|---|
| ID 与标题 | 稳定唯一编号；标题写明条件、动作和主要验证目标 |
| 目标与依据 | 一个主要验证目标；适用规则 ID、来源定位和范围；候选或冲突规则明确标记 |
| 风险与优先级 | 要防止的具体错误及业务后果；有依据的优先级或相对顺序 |
| 底线判断 | 已核定／候选／有替代／非底线／未评估；关联BL、核定范围、理由及替代，不由P0自动决定 |
| 设计状态／准备状态 | 分别记录预期是否确定，以及执行条件是否就绪 |
| 前置条件 | 操作前必须成立的环境、角色权限、数据范围、对象关系、状态及依赖；可引用共享前置并列出本例差异 |
| 测试数据引用 | 关联数据 ID／参数组，交代本例分配及数量、示例或实例性质；无新增造数时说明复用及核对要求 |
| 操作步骤 | 有序的角色、对象、输入和动作；并发时注明参与者、同步条件及顺序 |
| 预期与取证 | 每个断言的触发步骤、预期结果、规则、观察位置和判定标准；说明证据边界 |
| 影响与处理 | 数据和外部副作用、隔离措施、归属、清理／恢复／处置方式；无影响可说明不适用 |
| 缺口与关联 | 相关问题 ID、受影响断言、依赖和替代验证范围；无缺口可省略 |

不得仅用“正确”“正常”“成功”“符合需求”充当预期。描述能检查的状态、数值、对象关系、约束或错误结果。精确文案不是业务要求时，不额外把文案逐字相等设为通过条件。

一个用例按一个主要目标计数，参数行另计。独立门禁、不同状态路径或失败后果分开；不能写“遍历全部角色/全部依赖”替代各自可准备和判定的样本。同一一致性目标的必要链路可保留，说明为何多个步骤共同证明同一目标。

前置条件表达必须成立的事实，数据准备方案表达如何获得这些事实。数据清单及合法准备链统一按 [前置与数据准备设计](data-preparation-design.md) 编写；每条用例都要能定位到自己的数据要求和准备方式。查询类场景也需说明查询对象、分布或可复用基线；不强制所有用例新增数据。

同一目标的多个断言可写为：

| 断言 | 触发步骤 | 预期结果 | 依据 | 观察位置及证据限制 |
|---|---|---|---|---|
| A1 | 对应步骤编号 | 可判定结果／有依据的时限 | 规则 ID | 页面／接口／记录等；能证明与尚不能证明的范围 |

拒绝类用例应检查与目标有关的关键副作用未发生；异步用例不能把“请求已接收”作为最终处理完成的证据。未取得具体日志字段、数据库表名或接口定义时，写所需业务证据，不编造物理字段和查询命令。

## 设计状态与准备状态

两个维度独立记录，避免将“设计完成”当作“可以立即执行”。不记录未实际执行的通过／失败结果。

| 维度 | 状态 | 使用条件 |
|---|---|---|
| 设计 | 已明确 | 主要验证目标、适用依据、前置路径、所需数据及分配、准备检查点和判定方式已确定 |
| 设计 | 待规则确认 | 业务预期缺失、来源冲突，或用户尚未确认候选规则 |
| 设计 | 待设计补齐 | 前置路径、数据约束或数量分配、准备检查点、操作、断言或证据方案尚不足以支持目标 |
| 准备 | 已核实就绪 | 目标环境、角色、数据、依赖、观察及影响控制条件已有可引用的核实依据 |
| 准备 | 待准备 | 已知某项实际条件缺失，注明缺什么以及影响范围 |
| 准备 | 未核实 | 尚未验证实际执行条件；仅有设计材料时通常采用此状态 |

只有“已明确＋已核实就绪”支持“当前可执行”的表述。用户只要求设计时，不为了升级准备状态去登录系统、造数或执行操作。

实际执行中发现缺陷不等于设计不成立；是否暂停某路径由影响及执行控制条件决定。禁止把计划中的证据当作已取得的证据。

## 上游问题

每项问题包含：问题 ID、具体问题及来源、影响的规则／用例／断言、需要补齐的决策或条件、责任角色和状态。责任人和期限已有约定时引用；未指定时写“责任人待分配／期限待定”，可以建议责任角色，不编造承诺。

按问题性质标明下一步：

| 问题性质 | 需要补齐什么 | 对设计或执行的影响 |
|---|---|---|
| 业务决策 | 规则、冲突裁定、验收阈值或失败后的业务处理 | 受影响预期保留待确认草案；已明确部分继续设计 |
| 前置条件 | 合法准备路径、数据约束／数量／分配、环境、账号、权限或依赖 | 路径或需求不明时待设计补齐；方案明确而资源未落实时待准备 |
| 可观察性 | 足以判断目标的结果记录、查询能力或观测方式 | 标明缺失断言及当前证据上限；可拆出局部可验证目标 |
| 执行控制 | 隔离、副作用边界、恢复或处置方案 | 受影响操作待准备；不扩大为无关用例整体阻断 |

未决问题保留的是设计缺口，不预先登记成已确认系统缺陷。严重程度取决于具体业务后果和受影响范围。

## 可执行性与工具边界

人工检查、界面操作、接口调用、日志或数据查询都是可能的验证途径，按目标选择。自动化能力未确认时不声明 AI 可独立执行；人工或工具依赖明确列出。

模拟、桩或直接准备数据可以用于特定层次的隔离验证，必须说明省略的真实环节与结论限制。页面验证、服务端约束验证、真实集成验证按实际证据范围分别声明。

## 修订记录

按原 ID 标明保留、修改或废弃；新场景分配新 ID。修改记录写变更依据和影响；废弃保留理由及替代用例关联。用户要求精简时合并等价覆盖，仍保留旧 ID 与新位置的对应关系。
