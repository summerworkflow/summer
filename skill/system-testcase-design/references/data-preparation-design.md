# 前置条件与数据准备设计

用于回答：执行这些用例之前，必须具备什么条件，需要哪些数据，准备多少，如何得到，以及怎样确认已经准备好。本文件只约定设计产物，不授权实际造数、赋权、修改配置或执行脚本。

## 1. 从验证目标反推前置

按“验证目标 → 操作前必须成立的条件 → 数据与能力 → 准备方式”倒推，避免从现有数据反过来删减场景。

- 前置写可核对的事实，例如“付款单已审批、未付款、无进行中的支付请求，操作者有付款权限且在该单数据范围内”。
- 测试审批动作时，应从待审批状态开始；不能把审批通过当作准备动作完成，导致跳过被测环节。
- 负向场景明确本例故意不满足的条件，并让其他关键条件有效。例如无权限用例需有可操作的合法单据，避免先因单据状态错误被拦截。
- 只列相关的环境、开关、角色权限、对象状态、时间、外部依赖和观测能力。共享前置集中维护，单条用例引用并补差异。
- 无法确认前置是否能合法到达时，写明断点及所缺依据；不以“直接改成目标状态”补齐正常业务链。

## 2. 数据需求清单

给逻辑数据组分配稳定 ID，例如 DATA-001。逻辑 ID 不是实际单号；数据组中的具体记录和参数行有可区分的标识。清单可与用例放在同一文档中，以下内容可以按任务规模合并列。

| 内容 | 需要说明什么 |
|---|---|
| 数据 ID 与用途 | 对象／数据组、关联用例 ID 及参数行、支持哪个前置或断言 |
| 对象及关键约束 | 字段值或有依据的条件分区；金额、币种、精度、日期等只列相关项；示例值注明示例 |
| 状态及关系 | 准备完成时的对象状态、父子／来源关联、归属及权限范围、已有记录的有无 |
| 数量及分配 | 每例／每组／每轮需要多少，哪些共用同一对象，哪些必须不同；说明数量依据 |
| 来源与准备方式 | 复用、合法新建或加工、模拟／故障注入；引用可定位的已有流程或计划步骤 |
| 准备依赖 | 先有的主数据、角色权限、上游对象、接口或工具能力；未知能力列为缺口 |
| 完成检查点 | 哪些状态、数值及关系必须成立，从哪里核对；不能仅写“创建成功” |
| 复用与消耗 | 共享只读、独占可变或一次性消耗；并行、重复执行和参数组的分配规则 |
| 隔离与处理 | 与用例的影响处理方案关联；防串用标记、外部副作用及清理／处置方式 |
| 当前落实情况 | 计划／实际实例的区别；实际资源映射、核对证据及已知缺口，缺失时明确未核实 |

没有新增造数需求时，标为复用并给出筛选和核对条件；不能只写“使用现有数据”。没有业务对象数据时说明原因，仍保留相关账号、环境等前置。

未知字段、枚举、接口、表结构或合法值不得补造；先表达已知业务约束，并列出需要产品、开发或数据负责人补充的具体内容。已有代码或脚本只帮助定位准备能力，不自动成为业务预期。

## 3. 合法准备链

对新造或加工数据，从最早缺失的必要对象开始，写到用例操作之前的目标状态。可使用下面的表，也可引用已有可靠流程并写清本次参数和差异。

| 顺序与依赖 | 执行角色／已有能力 | 动作及输入 | 输出对象／状态 | 完成检查点 |
|---|---|---|---|---|
| SETUP-01；依赖的数据 ID | 实际已知的角色或流程定位 | 有依据的业务动作及参数 | 新逻辑 ID 或原对象新状态 | 可核对的状态、数值、关系及观察位置 |

每步输入应来自已说明的主数据、前一步输出或有依据的参数。不得循环依赖，也不能把“执行另一条测试用例”当作唯一准备方法。

选择准备方式时：

- 复用已有记录：说明筛选条件、当前状态、并发占用及使用前复核要求；存在记录不代表满足本次前置。
- 正常新建或状态加工：优先通过合法业务链；页面、接口或已有脚本是否适用，以当前授权和已知能力为准，不虚构菜单路径或工具命令。
- 模拟与故障注入：用于明确的隔离或防御测试，注明省略的真实环节及结论边界。前端无法输入的值，不能描述成可以在页面直接输入。
- 缺少能力：明确需要哪一步、何种输入输出、影响哪些用例。设计可保留待补齐部分，已明确子集继续交付；不因设计任务自动执行外部操作。

## 4. 数量、分配与复用

- 只读且基线不变的数据可共享；会改变状态、余额、库存或产生外部副作用的数据，默认按执行单元独占分配。可可靠恢复并复核基线时才说明复用方案。
- 一次性对象按用例、参数组及重复轮次计算数量。给出本次计划和计算依据；未指定轮次时给“每轮需求”，不编造总执行量。
- 并发或重复提交用例通常要多个操作者／请求指向同一个目标对象，明确对象关联；不要误造多个独立对象导致目标条件消失。
- 阈值和边界数据从已确认规则计算。时间相关数据还要说明业务时区、可用时间窗及刷新方式，不假设可以修改系统时钟。
- 为目标缺陷保留暴露条件。例如测试重复扣款时，资金或配额不足可能先拦截后续请求；在隔离范围内设计足够资源，说明需要的容量依据。
- 准备本身会消耗的数据和用于对照的数据也计入清单。共享数据不被某条用例的清理动作提前删除或改写。

## 5. 准备完成的判定

设计阶段可以完成数据清单及造数方案，真实账号、记录和环境尚未核实时维持准备“未核实”。实际确认缺少资源或能力时，相关用例为“待准备”。状态名称统一见 [用例契约](case-contract.md)。

只有实际核对后才记录“已核实”：目标环境、逻辑数据 ID 与实例的对应、状态／数值／关系、观察依据和核对时间。禁止把计划步骤写成“已创建”，或把示例编号当成真实数据。执行前仍需复核易变化的前置。

最终能沿“用例 → 前置 → 数据清单 → 准备链 → 完成检查点”追踪。用例、参数、规则或对象状态发生变化时，沿该关联更新数据数量、分配和检查方式，不重复维护同一份共享准备说明。
